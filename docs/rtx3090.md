# Qwen3.8 Flash Next on RTX 3090s

Branch `rtx3090` of leflakk/TensorFold: compute capability 8.6 and tensor parallelism over 1, 2, 4 or 8 GPUs of
one host, for `TensorFold/Qwen3.8-Flash-Next-MLX-4bit-MTP` (also published as `Vontra/...`).

## Which checkpoint

| | MLX 4-bit g32 + MTP (chosen) | EXL3 `4.05bpw_h6_ng6` |
| --- | --- | --- |
| GPU-resident bytes | 75.2 GiB (experts 70.3) | 63 GiB |
| Bytes read per decoded token (1 row) | ~4.2 GB | ~5.3 GB: dense layers at 6 bits, hyper-connections fp16 (1.28 GB) |
| Dequantization | shift + one fma per group: memory-bound | trellis decode: compute-bound on Ampere at 4 bits |
| Prompt speed (TensorFold, GB10) | 2,300-2,500 tok/s | 930-970 tok/s |
| Multi-GPU in TensorFold | yes (this branch: 2, 4, 8) | one GPU only (does not fit a 3090) |
| n-gram table | 32 GB (4-bit) | 39 GB (6-bit) |

EXL3 gives better quality per bit, but on Ampere the MLX checkpoint is the faster one for both prompts and decode.

## n-gram (PLE) tables

They stay on the host. Fastest: in RAM, locked (the default when the host has room: one rank reads them ahead and
`mlock`s them; raise the limit with `ulimit -l unlimited`). `--ple-on-ssd` reads each lookup from disk: a few
percent slower decode, ~32 GB less RAM. Every rank maps the same page cache, so the RAM is counted once.

## Host settings

- `ulimit -l unlimited` for the user that serves (e.g. `/etc/security/limits.d/99-tensorfold-memlock.conf`:
  `youruser - memlock unlimited`), or the n-gram tables cannot be locked and may page from disk.
- RAM: the 32 GB tables are pinned while the weights load (when the host has them plus 8 GiB free), so the
  checkpoint's other pages stay readable by every rank from the page cache.

## Install (no Docker)

```bash
git clone -b rtx3090 https://github.com/leflakk/TensorFold.git && cd TensorFold
python -m venv .venv && . .venv/bin/activate
pip install torch                      # any CUDA build of torch; nvcc of the same CUDA major for the JIT kernels
pip install -e .
hf download TensorFold/Qwen3.8-Flash-Next-MLX-4bit-MTP
```

The CUDA kernels compile on first start (a few minutes, once; cached in `~/.cache/torch_extensions`).


## Serve

```bash
HF_HUB_OFFLINE=1 tensorfold serve TensorFold/Qwen3.8-Flash-Next-MLX-4bit-MTP --tp 8 --host 0.0.0.0 --port 8080
```

Without `--master`, `--tp N` starts ranks 1..N-1 itself (one process a GPU, CUDA_VISIBLE_DEVICES with the rank's
GPU first). Rank 0 serves HTTP. Check drafted against serial output with `"draft": false` on a request.

`--tp 4` fits too (about 20 GiB of weights a GPU, a short KV window left); `--tp 8` leaves ~12 GiB a GPU for the
caches.

### Several requests at once: `--parallel N`

```bash
HF_HUB_OFFLINE=1 tensorfold serve TensorFold/Qwen3.8-Flash-Next-MLX-4bit-MTP --tp 8 --parallel 4 --host 0.0.0.0 --port 8080
python3 tools/bench_openai.py http://127.0.0.1:8080 MODEL --tokens 256 --reps 3 --concurrency 4
```

Up to N requests decode together, each stream's rows in one forward a round (all its verify rows, its MTP drafts
in one step a depth for every stream). Rank 0 decides every call (admissions, prompt passes, streams that ended)
and sends it through a ring in shared host memory before running it; the other ranks run the same calls, so their
collectives pair up and each rank samples the same tokens from the gathered candidates. Each reply equals its
request served alone (`same_as_alone` in the bench's `--concurrency` rows).

- The ranks must share the host (no `--master`); the window is admitted for one stream, the others' caches grow
  as they need while every rank has room (each rank's own memory, one agreed answer).
- Concurrent rounds run as CUDA graphs under `--tp` (`TF_MULTI_GRAPHS=0`: eager, 4x slower on 8x 3090): every
  stream's window is padded to `--mtp-drafts` + 1 rows, so one graph a stream count serves any streams (their rows,
  positions and cache pointers are tables refilled before each replay); the warm-up captures 1 to N streams,
  their first rounds included. A shape the warm-up missed (a context past 8,192 keys, a DeltaNet parity) is
  captured on its first round.
- A prompt that arrives while others decode fills in passes between their rounds (`--decode-share S` makes the
  passes short enough that a round takes S of a pass's time; 0, the default: whole 2048-row passes). A pass that
  holds one prompt runs as two overlapped halves, as the one-stream engine's chunks do.
- Not with `--parallel`: per-request `mtp_drafts`/`mtp_confidence`, logprobs, images; background requests keep
  their lane (they do not yield it under `--tp`).
- With `TF_PREFILL_COMM=nccl` (the default), NCCL's prompt sums round by size: a prompt can round differently when
  it shares a pass with others, and so reply differently from alone (still exact for its own prefill: drafts never
  change tokens). `TF_PREFILL_COMM=shm` keeps rank-ordered sums: replies equal alone, bit for bit.

## Variables

| Variable | Default | Meaning |
| --- | --- | --- |
| `TF_COMM` | `shm` | `shm`: partial sums through pinned shared host memory (rank-ordered fp32 sums, one kernel, graph-captured); `nccl`: NCCL all-gathers (upstream behavior) |
| `TF_PREFILL_COMM` | `nccl` | prompt-chunk sums (>1 MB): NCCL all-reduce (faster over PCIe); `shm` keeps rank-ordered sums, so a resumed prompt rounds exactly like a fresh one |
| `TF_PREFILL_PARTIALS` | `bf16` | prompt-chunk partials sent as bf16 (half the bytes) or `fp32` |
| `TF_DECODE_PARTIALS` | `bf16` | decode-window partials as bf16 or `fp32` (drafted rows equal serial ones either way) |
| `TF_FASTCOMM_SHOT` | `auto` | `1`/`2` one/two-shot with flags, `3`/`4` the LL forms (same bits); auto: `2` (measured fastest on 8x 3090) |
| `TF_FASTCOMM_GATHER_LL` | `1` | sampling candidates gathered in the LL form (7 us against 12.6 with flags) |
| `TF_PROFILE_DECODE` | unset | `N`: rank 0 prints every N rounds where a decode round's time went (adds a sync per phase; concurrent rounds too, with their streams a round) |
| `TF_GRAPHS` | `1` | `0`: the one-stream engine's decode windows run eager |
| `TF_MULTI_GRAPHS` | `1` under `--tp` | `--parallel` rounds and MTP steps as CUDA graphs (`0`: eager; `1` on one GPU too) |
| `TF_MULTI_GRAPHS_MAX` | `96` | captured round shapes kept (the oldest goes past it) |
| `TF_LOAD_DIRECT` | unset | `1`: read the checkpoint with O_DIRECT on every rank (default for local ranks: shared page cache) |
| `TF_PREFILL_OVERLAP` | `1` | prompt chunks as two halves whose NCCL sums overlap the other half's compute (+33-39% prefill on 8x 3090; ~5% of the KV window); `0`: whole chunks |
| `TF_EXPERT_SPLITS` | `8` | K splits of decode windows' expert gate/up on TP ranks (`1`: the unsplit kernel) |
| `TF_HC_DOWN`, `TF_HC_UPMIX`, `TF_ROUTER` | sm_86: tuned | decode kernels' launch shapes (`tools/tune_decode_kernels.py` finds them) |
| `TF_TOPK` | `triton` | sampling candidates by a two-pass Triton top-k; `torch`: torch.topk |
| `TF_NCCL_LIB` | found | path to libnccl.so.2 when the search (system, torch/lib, pip `nvidia/*/lib`) misses it |
| `TF_FASTCOMM_BLOCK_BYTES` | `2048` | bytes of a rank's share one block moves (smaller: more blocks, more PCIe requests in flight) |
| `TF_FASTCOMM_TIMEOUT` | `600` | seconds a rank waits for another before trapping |
| `TF_ISOLATE_GPUS` | unset | `1`: each rank sees only its own GPU |
| `TENSORFOLD_MEMORY_RESERVE_GIB` | 1.5 on 24 GB cards | what the startup budget leaves free on each GPU |

## Measured (8x RTX 3090, PCIe, no NVLink, EPYC 7532, one stream, up to `61a2ddb`)

| | |
| --- | --- |
| Startup | 125-168 s (n-gram tables locked during the load) |
| Window | 183,686 tokens at `--tp 8` |
| Decode, one stream, MTP | 194-245 tok/s (14.4-15.8 ms a round, sampled/greedy, chat/code), 278 tok/s on a code reply |
| Prefill | 3,170-3,650 tok/s (paired chunks; 2,400-2,600 whole) |
| Exactness | drafted and `"draft": false` replies have the same `token_sha` |

## Status

Done: sm_86 build (FP8 paths refused below 8.9), N-rank weight split (KV heads shared by rank groups, expert widths
96/64 at 8 ranks), host-memory collectives (bit-exact on 8x 3090, faster than NCCL for decode), multi-process
launcher, split-K experts for decode windows, paired prompt chunks, Triton sampling candidates. `--parallel` under
`--tp`: measured eager at `bb691fc` (1.9x the one-stream eager throughput at 2 streams, 3.1x at 4); rounds in CUDA
graphs and the 4-stream exactness fix (decode windows past 16 rows took other read-out kernels) not yet measured.

`tools/rows_check.py` checks, on one GPU at the real shapes, that no decode kernel gives a row other bits when its
window widens (1 to 64 rows): the property concurrent rounds rely on.
